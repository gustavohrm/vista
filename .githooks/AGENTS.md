# Agent instructions: `.githooks/`

## Traps

- An edited hook does not run when tried from a worktree the Claude desktop app created; the main checkout's copy runs instead. The app writes an absolute `core.hooksPath` pointing at the main checkout into the worktree's `config.worktree`, which `git config --show-origin --get-all core.hooksPath` shows. `scripts/install-hooks.mjs` sets the path with `--local`, which lands in the `.git/config` that every worktree shares, so a worktree inherits `.githooks` until the app's worktree-level value overrides it. Prefer `git -c core.hooksPath="$(pwd)/.githooks" <command>` to exercise the worktree's copy. Observed on git 2.53.0 for Windows with the desktop app of October 2026 in the codenhub repository these hooks come from, where a push of `claude/agent-branch-naming-03bee5` went through while the worktree's `pre-push` already refused that name; not separately reproduced in vista.
- A hook that is killed by a signal counts as passed: git proceeds and exits 0, so a rejected commit or push goes through with no message. The usual trigger is SIGPIPE, from piping git's output into something that stops reading early, such as `git commit ... 2>&1 | head -1`; a hook writing its rejection then dies mid-message. Each hook ignores SIGPIPE (`trap "" PIPE`), which covers that case only; a hook killed by SIGTERM or SIGKILL, from a timeout or an external kill, still passes. A hook that merely exits 141 is rejected as it should be. Prefer running git without such a pipe, or `| tail`, which reads to the end. Observed on git 2.53.0 for Windows in the codenhub repository these hooks come from; the trap is in every hook here, and Linux and macOS were not checked.
