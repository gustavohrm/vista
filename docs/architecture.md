# Application architecture

Vista separates shared product code from platform hosts:

- `packages/app` is the home for shared React UI, features, state, domain behavior, and platform capability contracts. It provides the application shell, workspace file explorer, document viewers/editors, and platform contracts.
- `apps/web` boots the shared app at the browser boundary using the File System Access API for local workspace access and is deployed as a Cloudflare Worker that also serves the desktop releases.
- `apps/native` boots the shared app at the Tauri boundary, using Tauri plugins (`@tauri-apps/plugin-dialog` and `@tauri-apps/plugin-fs`) for local filesystem access, plus `tauri-plugin-persisted-scope` so the granted folder scope survives restarts, `tauri-plugin-opener`, limited to revealing an entry in the file manager, and, on desktop, `tauri-plugin-updater` and `tauri-plugin-process` to update and restart the installed app. Its single Tauri project targets desktop, Android, and iOS.

Platform hosts MUST keep browser- or Tauri-specific implementations outside `packages/app`. Shared code MUST consume platform capabilities through narrow contracts. Add more workspace packages only when code has a proven independent responsibility or consumer.

## Platform adapters

The shared app owns capability interfaces; each host constructs and injects its implementations at startup. `AppAdapter` supplies host identity and capability interfaces such as `WorkspaceCapability`, `ThemeCapability`, and the desktop host's `WindowCapability`, which lets the app hold a window close until unsaved edits are answered for, and, through its optional `controls` (`WindowControls`), draw the window's buttons and move the window where the host has no system frame. Add capability contracts alongside their first product consumer, rather than building a generic adapter framework in advance.

- Hosts deal in folders, and the shared app owns workspaces. A host picks a folder, keeps access to it under a stable id, and reads and writes inside it; which folders form a workspace, its name and look, and its session are stored by the shared app, as [Stored workspace data](specs/workspaces.md#stored-workspace-data) describes. A host that knew about workspaces would duplicate that model in two adapters.
- Group operations by a specific capability, such as workspace access (`WorkspaceCapability`). Do not grow one flat interface containing unrelated host operations.
- Keep browser file handles, Tauri imports, native paths, and host permission APIs inside the hosts. Shared code consumes domain values and opaque identifiers defined by its contracts.
- Detect support per capability. A `web` or `native` label alone does not establish that an operation is available.
- Define cancellation, unavailable capabilities, permission denial/revocation, and observable failures when introducing an operation. Do not silently substitute different storage semantics.
- Specify ownership and cleanup when a capability introduces subscriptions, watchers, or other resources. Host construction and React rendering must not create unmanaged side effects.
- Test shared behavior with supplied adapters and test real platform boundaries in their owning host.

## Platform scope

The supported targets are the web app in current desktop Chrome and Edge, and the Windows native app. Linux is the second desktop platform: CI builds its installers and lints its Rust on every change, as [CI](ci.md#jobs) describes. macOS is not built or tested. The web host operates on user-selected existing folders via the File System Access API, rather than substituting browser-private storage. Writing in place and remembering folders require a secure context, the File System Access API, and user-granted permissions; other browsers fall back to a `webkitdirectory` input, which opens a folder for the session only and saves by downloading a file, as [Workspaces](specs/workspaces.md#platform-specific-implementations) describes. The native host uses Tauri's dialog and filesystem plugins.

Android and iOS are planned targets of the same Tauri host. The native host's README documents their project initialization and toolchain prerequisites; they have no folder access yet, and mobile builds and folder-access semantics require validation on those platforms before support is claimed. A shared web UI does not imply identical filesystem access across platforms.

The [File System Access API documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker) covers the browser constraints. [Workspaces](specs/workspaces.md) specifies the detailed workspace semantics and document handling.

## Shared presentation

The shared package owns the base stylesheet exposed as `@vista/app/style.css`. It composes:

- `@import "@codenhub/styles/tw";` (pinned to `0.11.0`, the first that reads the contrast and motion attributes [Appearance](specs/appearance.md#contrast-and-motion) describes) for Tailwind CSS v4 itself plus Codenhub design tokens, layout primitives, and component classes. This entrypoint imports Tailwind on its own, so the stylesheet MUST NOT also `@import "tailwindcss"`, which would emit Tailwind's Preflight twice.
- `@import "@codenhub/icons";` for base icon sizing and alignment rules.
- `@import "@codenhub/toaster/styles";` for the toast and confirmation dialog styles.

Class names use the Tailwind token utilities generated from the `@theme` tokens in `@codenhub/styles/tw` (for example `bg-surface`, `text-text-secondary`, and `border-border`). Components MUST NOT use arbitrary value classes that restate token variables, such as `bg-[var(--color-surface)]`.

Controls and surfaces use the `@codenhub/styles` component classes wherever one fits: `.btn` with its presentation, intent, size, and padding-step modifiers for text buttons, `.card`/`.panel` for floating surfaces and dialogs, `.ipt` for text inputs, `.data-table` in `.table-wrap` for the CSV view, `.checkbox` for Markdown task items, `.divider`, `.loader`, `.hint`, and the typography utilities. Tailwind utilities are for layout only, never to re-skin a package component. Two surfaces stay custom because the package has no component for them: workspace tree rows, and the full-pane editors (the CodeMirror raw editor and the Markdown editor), which are document surfaces rather than form fields. The raw editor's CodeMirror theme in `raw-editor.tsx` reads the same token variables (`var(--color-*)`, `var(--font-mono)`), since CodeMirror styles its own DOM. The shell's chrome is Vista's own, built on the same tokens, because the package's defaults suit a form rather than a dense workspace: its icon buttons are padded boxes with a tinted hover, and its tooltip is a large bubble that shows only on hover. Icon-only buttons in the shell (the title bar, explorer header, tabs, path bar, document actions, and find bar) use the `icon-button` utility in `style.css`, a square with no padding, a neutral hover, and a pressed fill, sized at each call site, so one 28 px button and one 24 px button share a look. Tooltips go through `packages/app/src/components/feedback/tooltip.tsx`, a compact bubble on the floating surface that shows after the pointer rests 400 ms, at once when another tooltip hid in the last 300 ms, and at once on keyboard focus, and hides on click and Escape. A bubble above or below its control measures itself as it opens and is centered unless that crosses the window's edge, so call sites never choose an alignment. A field edited in place, such as a CSV cell or a name in the explorer, adds `inline-field` to its `.ipt`: focused, it shows a hairline over the hover fill instead of the package's 3px focus ring, which made a cell look like a form. Dialogs, forms, and the start screen keep the package's `.btn`. What floats over the frame (menus, the palette, the find bar, dialogs, tooltips, and toasts) shares one floating surface: the `--color-pop` ground, a `--color-line-strong` edge, and the `--shadow-float` shadow, over a `--color-scrim` backdrop for modals. Menus, the button menus and every right-click menu, drop the shadow: they are the surface opened most often, the edge already sets them apart, and a soft drop shadow on each was read as a generic look rather than Vista's. Nor does a menu draw a focus ring on itself: it holds focus while no item does, as when opened with the pointer, and its items show focus with their fill. The exception is a menu with every item disabled, which keeps focus even from the keyboard: it shows the shell's hairline ring itself. `style.css` sets these on `.vista-menu`. Menus, the palette, the find bar, and Vista's own dialogs, such as the unsaved-changes dialog, stay `.card.soft.floating`, and `style.css` gives that card the surface through the package's hooks (`--ui-surface-ground`, `--ui-ink`, `--ui-surface-shadow`), since the soft card otherwise rests on the package's grey foreground. The toaster's confirmations are not cards: they take the same surface on the library's own classes, as [Toasts and confirmations](#toasts-and-confirmations) describes. The one recolour is `.btn.primary`, which takes the theme's action colours (`--color-action`, `--color-action-hover`, and `--color-action-text`): in Daylight, ink on light grounds and Daylight on dark ones, so the primary action carries Vista's colour instead of the package's blue. The focus ring and checkboxes take the theme's primary colour. Presentation passes down from a container in `@codenhub/styles`, so a button inside a `.soft` surface, such as a dialog, is soft too: a primary action there names its own fill (`btn primary solid`).

### Theming

`@codenhub/theme` (`packages/app/src/theme/theme-manager.ts`, pinned to `0.4.0`) sets the scheme and theme, stored under `vista-theme`, as [Appearance](specs/appearance.md#scheme-and-theme) describes: each theme is a light and a dark variant, such as `ocean-light` and `ocean-dark`, and `<html>` carries the theme's class, such as `theme-ocean`. `packages/app/src/theme/appearance.ts` writes the contrast and motion levels as `data-contrast` and `data-motion` on `<html>`, and its `useReducedMotion` replaces the motion library's hook, which reads only the operating system. Each host calls `initAppearance()` before it renders; the content security policy allows no inline script, so this runs at the start of the app's module script rather than in the page's `<head>`, and a slow load may briefly show the Daylight fallback before the saved appearance applies.

Colours are `light-dark()` tokens. The palette and the component tokens come from `@codenhub/styles`; `style.css` adds Vista's own tokens (the chrome and frame grounds, lines, the floating surface, selection, find matches, and the action colours) and sets the package's colour tokens Vista draws with, such as the text colours, the primary colour, and the focus ring. `@theme` names Vista's themed tokens with a placeholder value, so Tailwind generates their utilities, and one block per theme, `.theme-<id>`, gives every token its value; `packages/app/src/theme/themes.test.ts` checks each block sets them all. A theme class on any element shows that theme inside it, which is how Settings previews each theme. `:root[data-contrast="more"]` raises the text, lines, and fills over any theme, and the `contrast-more` class does the same inside one element, for the previews. The motion rules read `data-motion`; a motion preview in Settings plays from the `essential-motion` layer, past the package's reset, since it plays only when asked to. The [brand guidelines](guidelines/brand.md#colours) record each theme's measured contrast, which `apps/web/tests/e2e/appearance.spec.ts` checks.

### Toasts and confirmations

Transient messages and modal confirmations use `@codenhub/toaster`, pinned to an exact version (`0.4.0`) in the pnpm catalog. It is a vanilla DOM library, so `packages/app/src/components/feedback/toast.tsx` wraps one toaster instance (`createToaster`) and one dialog instance (`createDialogs`, from `@codenhub/toaster/dialog`) in a `ToastProvider` and exposes `useToast()` to React components. Toasts appear bottom-right with a close button and dismiss after 5 seconds. They take Vista's look from `style.css`, on the library's own classes, whose rules are all `:where` so Vista's win without `!important`: the floating surface the menus and tooltips use, with the kind shown by the icon's colour alone, so an info message is no louder than a menu and an error stands out by its red icon. The library's slide in from the edge, and the stack closing up, are kept. Confirmations use the library's native `<dialog>`, restyled the same way to the floating surface and the sizes of Vista's own unsaved-changes dialog, with no backdrop blur; its confirming button follows `.btn.primary` through the theme's action tokens, set on the `vista-dialog` class the dialogs are created with. Components call the wrapper and never touch the DOM nodes the library creates.

Product icons use `@codenhub/icons` configured in Vite with `mode: "svg"`, which rewrites `<i class="ic-...">` elements into inline SVGs at build/transform time. Decorative icons are hidden with `aria-hidden="true"`; icon-only controls MUST have an accessible name (`aria-label` or visually-hidden text). The rewrite is a static, build-time text match: the `ic-*` class MUST appear as a literal string in `className`. An icon name computed at runtime (for example, a template string selecting between two icon names) is not detected and renders nothing; branch to two literal `<i className="ic-...">` elements instead.

### Responsive layout

The application shell (`TitleBar`, `Sidebar`, `TabStrip`, `EditorPane`, `StatusBar` in `packages/app/src/app.tsx`) is responsive using Tailwind's default breakpoints, and is shared unchanged between the web host and the Tauri mobile targets named in [Platform scope](#platform-scope):

- `TitleBar` (`components/layout/title-bar.tsx`) is one 44px bar across the top, shown with or without a workspace. It holds the workspace switcher, the go-to-file field that opens the picker, and from `md` up the panel toggles, one `PanelToggle` per bar around the frame, so a later panel is one more entry; there is no menu bar and no theme toggle, as [Commands and menus](specs/workspaces.md#commands-and-menus) and [Settings](specs/workspaces.md#settings) explain. With no workspace open it holds only the switcher and the notice. Below `md` the go-to-file field shrinks to its icon, and a menu button at the left opens the explorer drawer. The desktop window has no system frame (`decorations: false`), so its host provides `WindowCapability.controls`. Where it does, `app.tsx` puts the title bar and `WindowButtons` (`components/layout/window-frame.tsx`) in one 44px row. A press on the row's empty part moves the window through `useWindowDrag`. Tauri's `data-tauri-drag-region` attribute would do the same, but it would put a host detail in the shared UI.
- `ActivityRail` (`components/layout/activity-rail.tsx`) is a narrow column at the left edge, below the title bar, from `md` up. It holds Explorer, the disabled Search and Graph buttons, and at its foot the desktop download in the browser and the Settings gear, as [Shell layout](specs/workspaces.md#shell-layout) describes. The fill behind the place the frame shows, the files or Settings, is one `motion` element with a shared `layoutId`, so it slides between buttons rather than fading out on one and in on the other. Below `md` the rail's buttons sit at the top of the explorer drawer instead, so the narrow layout loses no action. A layout without a rail, with the explorer toggle and menus in the title bar, was rejected: the rail reserves room for search and the graph and gives settings one fixed home.
- `TabStrip` (`components/layout/tab-strip.tsx`) is the tabs row: the tabs and, at its right end, the active document's view switch and Find, which `App` passes in. There is no document header: the path bar shows the path a breadcrumb would.

- Below `md` (768px): `Sidebar` renders as a dismissible overlay drawer (`fixed`, off-canvas when closed) that opens below the title bar (`top-11`), over a backdrop. The backdrop sits at `z-30` and the drawer at `z-40`. `TitleBar` is `relative z-50`, so it stays above both, and its drawer button is always reachable for closing. The toggle shows the panel's open/closed state via `aria-pressed`. Tapping the backdrop also closes the drawer. Selecting a file closes the drawer, since it covers the document underneath.
- `md` and above: `Sidebar` is the same persistent, in-flow column, 256px wide, and the title bar's Toggle Explorer shows or hides it: closing it collapses the column to zero width rather than overlaying content, and selecting a file no longer closes it, since it isn't covering anything. `app.tsx` keeps the user's choice (`isSidebarOpen`) apart from whether the column shows, which is also false while Settings shows, so closing Settings restores the choice. The column clips its content only while closed or opening, since a header tooltip must reach over the frame once it is open.
- Default state: the explorer opens by default at `md` and above (`packages/app/src/domain/viewport.ts`, `isDesktopViewport()`). Below `md` it starts closed, because the start screen in the editor area already offers the folder. Opening or reopening a folder then opens the drawer, so the files are the next thing a phone user sees. Crossing `md` while running follows [Shell layout](specs/workspaces.md#shell-layout): narrowing closes the explorer and widening restores the column as it was, through `onDesktopViewportChange()` in the same module.
- The shell has two grounds: the chrome (`bg-chrome`), which holds the title bar, rail, explorer, and status bar, and the frame (`bg-frame`), which holds the tabs row and the document or Settings. Each boundary is drawn once, by the frame's ground and its hairline (`border-line`); no bar has a border of its own, and the tabs row has no line under it. The tokens are Vista's own, defined in `style.css`, and reach the package's components through its documented tokens, such as `--ui-ink` for the line colour, which is how the package expects an app to replace its defaults. At `md` and above the frame is a panel with a 10px corner (`rounded-frame`) set into the chrome with an 8px margin, which closes up on each side where the rail, the explorer, the title bar, or the status bar meets it; below `md` it runs edge to edge without a hairline. The status bar sits under the frame column only, aligned to the frame's edges, and shows only while a file is shown. Shadows are kept for what floats over the frame, which shares one floating surface, as [Shared presentation](#shared-presentation) describes. Floating menus and the find bar use an 8px corner with 4px padding and 4px item corners, so the inner corners follow the outer one.
- With no file open, the editor area shows the start screen (`components/layout/start-screen.tsx`), which `EditorPane` receives as its `emptyState`. [Start screen](specs/workspaces.md#start-screen) specifies it. With no workspace open the start screen fills the window below the title bar, and neither the rail nor the explorer is shown.
- `TabStrip` shows one tab per open document above `EditorPane` and scrolls horizontally when tabs overflow. Open documents live in a reducer in `packages/app/src/state/documents.ts`; [Tabs](specs/workspaces.md#tabs) specifies their behavior.
- `StatusBar` is a bottom bar that shows nothing when no file is open. With a file open it shows the active file's path, with Copy and, on desktop, Reveal, on the left, and the raw editor's cursor and vim mode (only while the raw editor is shown) and the buffer's lines, size, line ending, format, and, for Markdown, word count on the right. [Path and status bar](specs/workspaces.md#path-and-status-bar) specifies them. It does not show platform identity or encoding.

A Tauri mobile webview reports its real viewport dimensions, so this works through ordinary CSS media queries with no `platform === "native"` branching required.

### Commands and shortcuts

User actions are `Command` objects (`packages/app/src/commands`): an id, a label, an optional shortcut, whether it is enabled, whether it is checked when it is a toggle, and what it runs. A `shortcutHint` names a key an editor handles itself, such as `Mod+Z`; menus show it, but the app does not bind it, so the key keeps working in every text field. `AppShell` builds the list from its state, and `useCommandShortcuts` installs one window `keydown` listener that runs the matching command. A disabled command still swallows its shortcut, so `Ctrl+S` with nothing to save never opens the browser's own Save dialog. Shortcuts are written like `Mod+Shift+S`, where `Mod` matches Ctrl or Cmd. The raw editor hands every command shortcut to this listener instead of handling the key itself, so a command wins over a CodeMirror or vim binding on the same key. Components MUST NOT add their own global shortcut listeners. Each command has a category, and the editor's right-click menu, the command list of the picker, and the Keyboard Shortcuts section of Settings read the same list, so an action and its shortcut are defined once. There is no menu bar. Every menu, including the explorer and tab menus, is drawn by one `Menu` component (`components/menu/menu.tsx`), which handles the keyboard, keeps inside the viewport, and returns focus to where it was before running the chosen action. Edit actions apply to the focused element (`commands/editing.ts`): CodeMirror's own commands in the raw editor, since it draws only the lines in view, and the browser's editing commands elsewhere.

The bound shortcuts are Save (`Mod+S`), Close Tab (`Mod+W` native, `Alt+W` web), Find (`Mod+F`), Replace (`Mod+H`), Go to File (`Mod+P`), Show All Commands (`Mod+Shift+P`), Go to Line (`Mod+G`), and Word Wrap (`Alt+Z`). The file, tab, find, go-to, and picker commands are disabled while the unsaved-changes prompt is open. [Commands and menus](specs/workspaces.md#commands-and-menus) lists every command. On macOS, `Cmd+H` is the system's Hide shortcut; since `Mod` also matches Ctrl, `Ctrl+H` opens Replace there, as does the find bar's disclosure button.

### Find

The find bar (`components/editor/find-bar.tsx`) owns the query and the UI and searches through a `FindTarget` (`components/editor/find-target.ts`), so it does not know which view it searches. The raw editor exposes a target over CodeMirror's search state (`raw-find.ts`), with CodeMirror's panel replaced by a hidden one, since its highlighting runs only while a panel is open. Rendered views share a DOM target (`dom-find.ts`) that walks the view's text and field values with the pattern from `domain/find.ts`.

## Hosting decision

The web app is hosted as a Cloudflare Worker, and the same Worker serves the desktop installers and the updater manifest from an R2 bucket. Clients download and update from that Worker rather than from GitHub Releases, so wherever the web app is hosted, the downloads are too. Each release also has a GitHub release, which carries its changelog entry but no installers. GitHub Actions still builds, signs, and publishes each release, so releases depend on GitHub as well as on the web app's host. A release deploys both together. [`docs/ci.md`](ci.md#releases) describes the workflow, the routes, and how long releases are kept.
